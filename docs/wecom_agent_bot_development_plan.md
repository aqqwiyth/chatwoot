# 微信客服渠道 Agent Bot 兜底与平台会话状态同步开发方案

| 文档信息 | 内容 |
| --- | --- |
| 版本 | v1.2 |
| 整理日期 | 2026-10-22 |
| 适用系统 | Chatwoot 微信客服渠道 |
| 需求范围 | 需求一：Bot 异常及超时兜底；需求二：平台会话状态投递与同步 |
| 当前阶段 | 开发完成，已热更到现有 Docker 容器；真实 Bot 与微信账号的完整业务联调待验收 |

## 1. 背景与建设目标

微信客服渠道将客户消息投递给下游 Agent Bot 后，需要在 Bot 异常或长时间没有回复时，将会话交给人工处理。同时，Bot 需要获取微信平台当前的会话接待状态，避免在人工已经接入或会话结束后继续按机器人接待流程处理。

本次建设目标：

1. 在微信客服渠道提供可配置的兜底策略。
2. Bot 投递异常或超过配置时间没有有效回复时，转入所选人工接待渠道。
3. 向 Bot 投递消息及关联平台事件时，附加微信平台会话状态。
4. 通过平台事件、转人工结果及每 10 分钟的 API 查询维护状态；查询失败保留上次状态。
5. 通过轮次标识、会话锁和任务去重，处理连续消息、迟到回复及并发转人工。

## 2. 业务口径与范围

### 2.1 已确认规则

| 事项 | 确认方案 |
| --- | --- |
| 兜底目标 | 微信平台人工客服、Chatwoot 人工客服，二选一 |
| Chatwoot 分配方式 | 沿用收件箱现有成员、团队及自动分配规则，不增加指定坐席配置 |
| 超时起点 | 每条新的客户消息开始新一轮计时，连续消息以最后一条为准 |
| 有效回复 | 微信发送 API 成功接受的客户可见文本或附件 |
| API 校准间隔 | 10 分钟，异步执行；实际触发受扫描和队列调度影响 |
| API 查询失败 | 保留上次有效状态及观测时间；首次查询失败为未知状态 |
| 升级默认行为 | 兜底默认关闭，已有渠道需主动开启 |

### 2.2 两套会话状态

Chatwoot 会话状态与微信平台接待状态分别保存，不作简单等价映射。

- Chatwoot 状态：如 `pending`、`open`、`resolved`，用于机器人接待、人工队列及工单管理。
- 微信平台状态：`service_state`，用于表示微信客服平台的实际接待阶段。

| 微信 service_state | 含义 |
| --- | --- |
| 0 | 未处理 |
| 1 | 智能助手接待 |
| 2 | 待接入人工、排队中 |
| 3 | 人工接待中 |
| 4 | 会话已结束或尚未开始；客户尚未发送上行消息 |
| null | 尚未取得有效状态 |

### 2.3 本期边界

- 保持现有 Bot 异步 Webhook、消息创建 API 及主动 handoff 入口。
- 不对任意 HTTP 200 响应体猜测业务错误含义；2xx 表示接收投递，后续是否回复由超时规则判断。
- 不新增 Chatwoot 指定坐席或团队配置。
- 不改变其他渠道和 Enterprise Captain 的通用转人工语义。

## 3. 需求一：Bot 异常与超时兜底

### 3.1 配置流程

入口：设置 → 收件箱 → 微信客服 → 配置 → Bot 兜底。

配置步骤：

1. 为收件箱关联并启用 Agent Bot。
2. 完成 Bot 回复轮次 token 的回传适配。
3. 开启自动兜底，填写无回复超时秒数。
4. 选择微信平台人工或 Chatwoot 人工，保存配置。
5. 使用测试会话验证正常回复、投递异常及超时转接。

| 配置字段 | 类型 | 默认值 | 约束 |
| --- | --- | --- | --- |
| bot_fallback_enabled | boolean | false | 关联并启用收件箱 Bot 后生效 |
| bot_fallback_timeout_seconds | integer | 30 | 1～3600 秒 |
| bot_fallback_target | string | wecom_platform | 仅支持 wecom_platform、chatwoot |

前端提供保存状态、错误提示、数据回显及输入校验；后端同步校验字段类型、范围和目标枚举。

### 3.2 规则一：下游投递异常

适用对象为处于 Bot 接待中的客户 incoming 消息投递。以下情况进入异常处理：

- HTTP 非 2xx。
- 连接失败、请求超时等网络异常。
- 按现有规则可重试的错误在重试耗尽后失败。

消息更新通知、平台事件、Bot 自身消息及人工消息的投递失败，不启动新的自动转人工。

现有 Webhook 中 429、500 按既有机制重试；其他失败进入失败处理。无回复超时任务可以先于重试耗尽触发兜底，但同一轮只领取一次处理权。

### 3.3 规则二：超过配置秒数无有效回复

每条新客户消息生成一轮 token，并保存客户消息 ID、Bot ID 和截止时间。新的客户消息替换当前轮次，原轮次的超时任务即失效。

示例：超时设置为 30 秒，客户在 10:00:00 发送 A，在 10:00:20 发送 B。兜底截止时间更新为 10:00:50，A 对应的 10:00:30 超时任务不执行转接。

| 行为 | 是否解除本轮等待 |
| --- | --- |
| 携带正确轮次 token 的 Bot 文本或附件被微信 API 成功接受 | 是 |
| 人工成功发送回复，且回复创建时间不早于当前客户消息 | 是 |
| 仅在 Chatwoot 创建消息、默认状态显示 sent | 否 |
| 私有备注、handoff 命令、附件仅上传成功 | 否 |
| 微信发送失败 | 否 |
| 旧轮次 token 的 Bot 回复 | 否；不允许跨轮次发送 |
| 未回传 token 的 Bot 回复 | 可兼容发送，但不解除等待 |

重复同步、历史消息、平台事件、客服回声和消息编辑不重置截止时间。延时任务受队列调度影响，配置秒数表示最早达到触发条件的时间。

### 3.4 两类人工接待路径

| 目标 | 执行行为 | 特殊情况 |
| --- | --- | --- |
| 微信平台人工 | 结束 Bot 接待，查询平台状态及在线客服，调用微信转接接口 | 已人工接待则不重复转；无在线客服进入状态 2，每 3 分钟检查；已结束不强制转接 |
| Chatwoot 人工 | 执行完整 Bot handoff，打开会话并交回现有人工分配流程 | 微信平台实际状态独立保留，人工使用现有渠道发送接口回复 |

微信平台转接失败时，保留 Chatwoot 可人工处理的交接状态并记录失败原因，不自动切换为另一个配置目标。提示语发送失败单独记录，不能将已成功的人工转接回滚。

### 3.5 并发与接待轮次

- 短事务领取兜底执行权、写入停止标记并完成 Chatwoot handoff；微信外部 API 调用放在事务外。
- 执行结果和失败原因分别落库，避免微信已转接、本地却回滚为 Bot 接待。
- 使用会话级任务互斥，异常与超时并发不产生重复交接。
- 人工排队使用独立 poll token，原超时和异常任务不能创建额外轮询链。
- 每次实际发送文本或媒体前，重新校验 Bot 身份、轮次及接待权限，并与停止动作使用会话锁协调。
- 关闭配置、停用或更换 Bot、会话结束及旧轮次任务，不执行原来的等待兜底。
- 会话重新进入 Bot 的 pending 接待并收到新客户消息后，可以恢复新轮次；仅已确认平台状态为 0、1 时启动回复等待；状态为 2、3、4 或未知时仍投递 Bot，但不启动无响应兜底。

## 4. 需求二：平台会话状态投递与同步

### 4.1 状态存储

新增微信平台会话状态表，以 `channel_id + external_userid` 作为唯一键，避免 Chatwoot 新建会话后丢失同一微信客户的最近状态。

| 字段 | 说明 |
| --- | --- |
| channel_id | 微信客服渠道 ID |
| external_userid | 微信客户标识 |
| service_state | 平台状态，未知时为 null |
| servicer_userid | 当前平台接待人员标识 |
| source | 状态来源：unknown、event、handoff、api |
| observed_at | 最近有效状态的观测时间 |
| next_refresh_at | 下次 API 查询计划时间 |

为唯一键及刷新时间建立索引；渠道删除时同步清理关联状态记录。

### 4.2 状态更新入口

1. **微信平台事件**：先更新状态，再保存和投递关联事件，使 Bot 收到事件时附带更新后的状态。
2. **转人工结果**：主动 handoff、自动兜底及排队检查取得有效平台结果后，写入同一状态存储；失败不写入期望目标状态。
3. **API 查询校准**：使用现有 `kf/service_state/get`，异步取得平台实际状态。

平台事件的 `change_type` 与 `service_state` 是两套枚举，显式映射如下：

| session_status_change.change_type | 对应 service_state |
| --- | --- |
| 1：接入人工 | 3 |
| 2：等待接入人工 | 2 |
| 3：结束人工接待 | 4 |
| 4：重新接入已结束或已转接会话 | 3 |

进入会话及无法直接判断状态的事件触发异步查询，不凭事件名称编造状态。

### 4.3 每 10 分钟校准

- 调度器每分钟扫描到期记录，按每批 100 条投递独立刷新任务。
- 单个微信平台会话按 10 分钟间隔校准。
- 仅对有关联未结束 Chatwoot 会话、且平台状态不为 4 的记录执行周期 API 查询。
- 新客户消息或进入会话事件可重新触发异步查询。
- 不阻塞 Bot 消息投递；到期任务通过锁及刷新时间去重。
- 查询失败保留原状态和观测时间，下次尝试延后 10 分钟。

### 4.4 状态一致性

- 较旧时间戳的事件不得覆盖较新状态。
- API 查询开始前记录状态观测快照，返回后在行锁内核对；期间已有新的观测则丢弃查询结果。
- 平台状态为 2、3、4 时停止旧 Bot 等待。
- 首次没有有效状态时保持 null；无客户标识、不能关联的事件携带 `platform_session: null`。
- 超过 10 分钟没有有效观测时，通过 `stale` 告知 Bot 当前快照可能过期。

### 4.5 主动调用 service_state/trans 的同步边界

微信 `/cgi-bin/kf/service_state/trans` 成功后变更微信平台会话状态或接待人员。本地同步须区分操作入口：

| 操作入口 | 本地同步机制 |
| --- | --- |
| Bot 经 Chatwoot 主动 handoff | 微信操作成功后，由 HandoffService 立即保存有效平台状态，不等待回调或定时校准 |
| Chatwoot 自动兜底转微信人工 | 使用相同服务，立即保存成功结果 |
| 外部 Bot 或其他系统直接调用微信 trans | Chatwoot 不会立即获知；依靠实际收到的平台回调，或后续符合条件的 API 查询 |

内部流程保存 `service_state`、`servicer_userid`、`observed_at`，状态来源记为 `handoff`；状态 2、3、4 同时取消关联会话的 Bot 回复等待。接口失败不将期望目标状态写成成功；转接提示语失败单独记录，不回滚成功转接。

“同步到会话”当前指：平台快照按 `channel_id + external_userid` 独立保存，由关联会话读取，后续向 Bot 投递时附在 `platform_session` 中。它不直接覆盖 Chatwoot 的 `pending/open/resolved`，也没有新增会话详情 API 字段或客服页面状态展示。

不能假设每次外部 trans 都必然产生可用回调。未收到回调时，定时校准受活跃会话、非状态 4、扫描及队列条件约束，不保证外部操作后立即同步。当前没有新增外部“状态变更成功”回传 API；即时同步应走现有 Chatwoot handoff 流程，或另行设计实现成功回传入口。

## 5. 接口及数据契约

### 5.1 保存渠道配置

复用现有收件箱 API，不新增配置端点。更新请求：

```http
PATCH /api/v1/accounts/{account_id}/inboxes/{inbox_id}
```

```json
{
  "channel": {
    "bot_fallback_enabled": true,
    "bot_fallback_timeout_seconds": 30,
    "bot_fallback_target": "wecom_platform"
  }
}
```

收件箱查询与更新响应返回上述三个配置字段，支持页面回显。

### 5.2 投递给 Bot 的扩展字段

以下示例仅展示新增字段；原有消息、账户、收件箱和会话字段继续保留。

```json
{
  "wecom_bot_fallback": {
    "token": "delivery-round-token",
    "bot_id": 123
  },
  "platform_session": {
    "provider": "wecom_customer_service",
    "channel_id": 1,
    "open_kfid": "wk...",
    "external_userid": "wm...",
    "service_state": 1,
    "servicer_userid": null,
    "observed_at": "2026-10-22T10:00:00Z",
    "source": "api",
    "next_refresh_at": "2026-10-22T10:10:00Z",
    "stale": false
  }
}
```

`wecom_bot_fallback` 出现在符合条件的新客户消息投递中；平台事件不启动回复计时。关联平台事件采用 `wecom_sync_message`，保留 `raw_message` 和会话信息，不依赖普通 activity 消息过滤规则；事件记录的后续更新不重复投递该平台事件。

### 5.3 Bot 回复回传 token

Bot 使用现有消息创建 API，并回传原请求中的轮次 token：

```http
POST /api/v1/accounts/{account_id}/conversations/{conversation_display_id}/messages
```

```json
{
  "content": "您好，以下是处理结果。",
  "message_type": "outgoing",
  "private": false,
  "extensions": {
    "wecom_bot_fallback_token": "delivery-round-token"
  }
}
```

必须回传该次请求的原 token，不能在生成回复时读取最新 token 替代，否则无法区分迟到回复的归属。此 token 用于轮次关联，不替代 API 身份认证。

## 6. 技术实现与职责分工

| 子系统 | 主要职责 |
| --- | --- |
| 渠道模型与数据库迁移 | 配置字段、类型及范围校验、平台状态表与索引 |
| 收件箱 API 与前端组件 | 配置保存、回显、秒数与目标选择、Bot 适配说明 |
| AgentBotListener | 附加平台状态，客户新消息生成兜底上下文，补齐平台事件投递 |
| BotFallbackService / BotFallbackJob | 轮次管理、超时与异常处理、短事务交接、结果落库和排队去重 |
| HandoffService | 复用微信人工接待能力，支持主动命令和会话级自动兜底 |
| MessageBuilder / SendOnChannelService | 回复轮次标记、实际发送权限校验、成功发送后解除等待 |
| PlatformSessionService | 统一写入状态、事件映射、API 查询、失败保留及并发校验 |
| RefreshPlatformSession(s)Job | 到期扫描、异步刷新、活跃会话筛选 |
| Webhook Trigger | 将符合条件的投递失败交给微信专属兜底入口 |

微信专属规则保持在渠道服务中，不修改通用 `bot_handoff!` 的语义；保持 Enterprise presenter 的扩展契约。新增界面及服务端文案按仓库约定维护英文源语言。

## 7. 开发及上线计划

| 阶段 | 交付内容 | 完成条件 |
| --- | --- | --- |
| 1：基础设计 | 业务口径、配置和 payload 契约 | 两类目标、最后一条消息计时及 token 规则明确 |
| 2：状态同步 | 状态模型、事件更新、API 校准和 Bot payload | 失败保留旧值，事件与查询不覆盖新状态 |
| 3：兜底策略 | 异常、超时、转人工、轮次和互斥 | 同轮只交接一次，旧任务和回复不跨轮次生效 |
| 4：配置界面 | 独立组件、API 字段及校验 | 保存、回显、默认值和输入限制一致 |
| 5：验证与发布 | 隔离断言、生产构建、迁移、热更和接口检查 | 服务健康、资源与 API 字段验证通过 |
| 6：业务验收 | Bot token 适配、真实微信会话和人工接待联调 | 下表中的业务场景由实际接待链路验证 |

正式重建镜像时，应包含本次源码、前端资源和数据库迁移。当前已完成的是现有 Docker 容器热更；仅重启现有容器与重新创建容器的持久化范围不同。

## 8. 验收标准

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| A01 | 未启用兜底或未启用收件箱 Bot | 不执行新自动兜底策略 |
| A02 | 保存配置后刷新页面 | 开关、秒数、目标正确回显；非法值拒绝 |
| A03 | Bot 投递 HTTP 失败、网络异常 | 依据既有重试规则进入所选人工目标 |
| A04 | Webhook 2xx，但没有后续有效回复 | 达到截止时间后兜底 |
| A05 | 客户连续发送两条消息 | 第二条重新计时，第一条超时任务失效 |
| A06 | 正确 token 的文本或附件成功发送 | 解除对应轮次等待 |
| A07 | 私有备注、上传成功但发送失败 | 不解除等待 |
| A08 | 旧 token 或无 token 回复 | 旧 token 不跨轮次发送；无 token 不解除等待 |
| A09 | 异常与超时并发、重复任务 | 同轮只领取一次交接；不产生重复排队链 |
| A10 | 微信目标无在线客服 | 进入排队，按现有 3 分钟间隔检查 |
| A11 | Chatwoot 人工目标 | 完整 handoff，沿用原有人工分配规则 |
| A12 | 已转人工、结束或切换 Bot | 旧任务不重新接管；停止后的旧 Bot 回复不发送 |
| A13 | 会话重新进入 Bot 接待并收到新客户消息 | 仅已确认状态 0、1 开始新轮次；2、3、4 和未知状态不启动等待 |
| B01 | 人工接入、排队、结束事件 | 状态先更新，随后 Bot 投递携带对应状态 |
| B02 | 主动 handoff 或自动兜底成功 | 统一状态存储与后续 payload 一致 |
| B03 | 活跃会话到达校准周期 | 异步查询 API，不阻塞消息投递 |
| B04 | API 失败或首次失败 | 保留上次有效值；首次为未知，不冒充状态 0 |
| B05 | 查询期间收到平台事件 | 查询旧结果不得覆盖新观测 |
| B06 | 较旧事件、重复同步或事件记录更新 | 状态不倒退，不重复启动等待或投递关联事件 |
| C01 | 其他渠道、既有主动 handoff、Enterprise 扩展 | 保持原有适用行为 |

## 10. v1.1 补充：按平台状态决定是否等待回复

| service_state | 是否投递 Bot | 是否允许普通 API 回复平台 | 是否启动回复等待和异常兜底 |
| --- | --- | --- | --- |
| 0、1 | 是 | 是，还需满足当前接待人及轮次权限 | 仅对符合条件的客户新消息启动 |
| 2、3、4 | 是 | 否 | 否；旧等待任务也需复核并退出 |
| 未知 null | 是 | 否，等待有效状态确认 | 否，不推断为 0 |

缓存仍为 4 或未知时，新客户消息可触发异步查询，但该次投递不要求 Bot 回复；状态确认后，后续符合条件的新客户消息才启动等待。已转人工后的排队检查用于继续完成人工接入，不属于 Bot 无响应等待，不因状态 2 被取消。

专用事件提示接口独立处理；本表限制的是普通消息 API。已结束会话由接待人员在客户端重新接入时，`change_type=4` 映射为 `service_state=3`，不启动 Bot 回复计时。
